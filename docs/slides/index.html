p2c

Two daemons. What could we do?

1. Make them match

# libs.versions.toml
kotlin = "2.4.0"
# build-logic/
# gradle.properties
kotlin.daemon.jvmargs=
(same as root)

Same compiler as Gradle, same memory request.

→ One daemon, 4 of 4 runs. Recheck on every Gradle upgrade.

2. compilerVersion

# build.gradle.kts
kotlin {
  @OptIn(…)
  compilerVersion
    .set("2.4.0")
}

Keep your KGP, run another compiler (Build Tools API).

→ Kotlin’s direction. Experimental; not tested by us.

3. Let idle daemons exit

# gradle.properties
org.gradle.jvmargs=… \
  -Dkotlin.daemon.options=
  autoshutdownIdleSeconds
  =60

Default: an idle Kotlin daemon lives 2 hours.

→ Still two, but each exits 60 s after its last compile.

Official fix: none yet. gradle/gradle #34755 is open.

AGP IS BUILDING

BuildConfig: not implemented in the KMP library plugin. The docs suggest BuildKonfig or a similar tool. Build-type values belong in the app module (our inference).

Debug-only dependencies: debugImplementation becomes "androidRuntimeClasspath"(...) for tooling such as Compose preview (AGP 9.0.0-beta01+). Dependencies for debug builds only (a debug menu) go in the app module (our inference).

One variant, nothing to guess: a 12-variant app consumed it with no fallback config (measured). Legacy KMP on com.android.library fails on AGP 9 unless you opt out with two deprecated flags; removal expected in AGP 10.0.

On by default: planned for Gradle 11.

KEEP IT AT ZERO PROBLEMS

AvoidDo instead
Reading files, env vars or system properties directlyproviders: fileContents, environmentVariable
project inside a task actiontask inputs, injected services
Running a process while configuringproviders.exec, or do it in a task

p3d3

Storing the cache is easy. Getting a hit is hard.

A hit needs every recorded input to match the last build:

The same tasks, with the same arguments

The same scripts, build-logic, catalog, gradle.properties

The same env vars, system properties and files read while configuring

The same JDK running Gradle: 17 → 21 says JVM has changed

IDE vs terminal: Studio passes its own Gradle property, so each switch misses

SNAPSHOT or dynamic versions: an entry lives only as long as their resolution is cached

The same checkout and machine: entries sit in .gradle/configuration-cache, encrypted per machine

A CI agent that survives: ephemeral runners start with no entries

Every build stores an entry. Far fewer reuse one. When you can’t skip it, spread it.

p3e0

Isolated Projects: when you can’t skip it, spread it

CONFIGURATION CACHE

Hit: skip configuration.

Miss: configure every project, one after another.

+ ISOLATED PROJECTS

No project touches another’s state, so projects configure in parallel.

Turns the cache on; stores it in parallel.

Where it helpsWhat changes
IDE syncSync never hits the cache; parallel configuration is the only speed-up
Cache missesAfter any build-file change, CI with a fresh checkout
Next (planned)Reconfigure only the projects that changed

Limits today: every project is still configured, children wait for parents, more memory. The ceiling is configuration’s share of the build.

HOW TO REACH ZERO, AND STAY THERE

1. Configuration cache at zero problems first.

2. List every violation: diagnostics mode.

3. No allprojects / subprojects: use convention plugins.

4. No properties from the parent project.
